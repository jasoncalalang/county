# Plan: W3 order history (`order_event`)

Date: 2026-11-28. Work item: `docs/agent-playbook.md` W3. Spec: functional spec §3.4
("a history of status changes with timestamps"). ADRs: 0012 (orders immutable), 0013 and
0015 (lock order). Next free migration: `V6`.

## 1. Scope and non-goals

In scope:

- Record one `order_event` row for every successful order action (confirm, cancel by
  owner, cancel by reseller, deliver, mark paid), in the transaction that changes the order,
  with who did it and when.
- Return the events on `GET /api/orders/{id}`, on the owner action responses and on
  `GET /api/order/{token}/orders/{id}`.
- Owner order detail page renders its history from the events, with actor names.

Non-goals (YAGNI):

- No event for placement. `placedAt` already records it and the actor is always the reseller.
- No backfill. Orders changed before V6 have no events (playbook W3).
- No `reason` column: no action takes a reason today.
- No history on the reseller's web order page, the order list, quotes or resellers.
- No general audit trail of other entities.
- Not inverting the existing `persistence` → `api` dependency (`Views`, `Problem`). Every
  service has it today; inverting it is its own work item. New classes follow the existing
  pattern and must not make it worse (see §3).

## 2. Threat model

Assets: the integrity of the history (it is the record of who confirmed, delivered and took
payment); the owner's personal data (`app_user.id`, `display_name`, `email`); each tenant's
order data.

Actors: owner; reseller holding a link; anonymous caller; owner of another tenant.

Entry points: the six existing order endpoints below. No new endpoint.

| # | Abuse case | Control | Test |
|---|---|---|---|
| A1 | Owner of tenant B reads tenant A's order history | Order lookup is tenant-scoped; events are read by `(tenant_id, order_id)` | T7 |
| A2 | Reseller reads the history of another reseller's order in the same business | Public lookup is scoped to the token's reseller | T8 |
| A3 | A link holder learns the owner's personal name, email or user id | Public view shows the business name for owner events and carries no actor ids | T6 |
| A4 | A caller names another actor in the request | Actor comes only from the verified subject or the token; no input carries one | T9 |
| A5 | Failed or forbidden attempts leave rows that read as history | The event is written only after the rule check passes, in the same transaction | T4, T5 |
| A6 | A retry or a race records an action twice | The order row lock serialises actions; the second one fails the rule check | T5, T11 |
| A7 | History is edited or deleted after the fact | No API writes events except the actions; a database trigger rejects `UPDATE` and `DELETE` on `order_event` | T10 |
| A8 | Anonymous caller reads history | Owner endpoints need a verified token (existing 401 test); an unknown or blocked link is `404` | existing, T8 |

## 3. Design

### Migration `V6__order_events.sql`

```sql
CREATE TABLE order_event (
 id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 tenant_id BIGINT NOT NULL,
 order_id BIGINT NOT NULL,
 at TIMESTAMPTZ NOT NULL,
 from_status VARCHAR(10) NOT NULL CHECK (from_status IN ('placed','confirmed','delivered','cancelled')),
 to_status VARCHAR(10) NOT NULL CHECK (to_status IN ('placed','confirmed','delivered','cancelled')),
 paid BOOLEAN NOT NULL,
 actor_type VARCHAR(8) NOT NULL CHECK (actor_type IN ('owner','reseller')),
 actor_user_id BIGINT REFERENCES app_user(id),
 actor_reseller_id BIGINT,
 FOREIGN KEY (tenant_id, order_id) REFERENCES sales_order(tenant_id, id),
 FOREIGN KEY (tenant_id, actor_reseller_id) REFERENCES reseller(tenant_id, id),
 CHECK ((actor_type = 'owner' AND actor_user_id IS NOT NULL AND actor_reseller_id IS NULL)
     OR (actor_type = 'reseller' AND actor_reseller_id IS NOT NULL AND actor_user_id IS NULL))
);
CREATE INDEX order_event_order_idx ON order_event (tenant_id, order_id, at, id);
```

plus a `BEFORE UPDATE OR DELETE` trigger that raises an exception (A7). `paid` is the order's
paid flag after the event. Mark paid is the event with `from_status = to_status = 'delivered'`
and `paid = true`; deliver-and-paid is one event `confirmed → delivered` with `paid = true`.
Works on Postgres 16 and 17.

### Code

- `domain/OrderRules`: unchanged rules. Statuses and actors stay enums; new code passes the
  enums, converting to the stored lowercase string in one place.
- `persistence/OrderEvent` (new entity) and `persistence/OrderHistory` (new service,
  `@ApplicationScoped`): `record(order, from, to, actor ids, at)` and the read side that
  returns the events of one order, oldest first (`at`, then `id`), for the owner or for the
  reseller.
- `persistence/OrderActions` (new service): one method per action, `confirm`,
  `cancelByOwner`, `cancelByReseller`, `deliver(paid)`, `markPaid`. It takes over
  `Orders.transition`, which is deleted: that method branches on a target string and on which
  of `subject`/`token` is null, which the engineering rules forbid, and `Orders` is already
  large. `OrderActions` injects `java.time.Clock` and `OrderHistory`. A `Clock` producer
  (system UTC) is added; nothing else moves to the clock in this item.
- Lock order is unchanged: reseller (reseller cancel only), then the order. The owner's user
  id is read without a lock. An `order_event` row is inserted in the same transaction and is
  never locked, so it is not a lock target under ADR 0015; say so in `api/README.md`.
- `api/OwnerOrderResource` (new): the owner order endpoints (`GET /orders`,
  `GET /orders/{id}`, the four actions) move out of `OwnerResource` unchanged in path, auth
  and behaviour. `OwnerResource` shrinks. `ResellerResource.cancel` calls `cancelByReseller`.
- `Views.OrderEvent(at, fromStatus, toStatus, paid, actorType, actorName)`, schema name
  `OrderEventView`. `Views.Order` gains `List<OrderEvent> events` (empty list, never null).
  - Owner view: `actorName` is the owner's `display_name` (nullable) or the reseller's name.
  - Reseller view: all events of that order; for owner events `actorName` is the business
    name. No ids, no email, in either view.
- OpenAPI: only the `OrderEventView` schema and `OrderView.events` change. Moving endpoints
  to a new resource class must leave paths, operations and schemas otherwise identical;
  inspect the diff.
- Web: `OrderEventView` and `events` in `web/lib/api-types.ts`; a pure
  `orderHistory(order)` in `web/lib/dashboard/orders.ts` returning `{label, at, by}` entries;
  the order detail page renders them; `web/e2e/fake-api.mjs` records events the same way.
  Labels: "Placed" (from `placedAt`, by the reseller name), "Confirmed", "Cancelled",
  "Delivered", "Delivered and paid", "Marked paid". Owner with no display name reads
  "Owner". An order with no events (changed before V6) falls back to its timestamps, without
  names.
- Docs: `api/README.md` (history paragraph, lock note), playbook status board W3 → done.
